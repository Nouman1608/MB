Section 7.5 of Cambridge IGCSE ICT 0417 covers the characteristics, uses and purpose of technical and user documentation and the components of each. These notes condense the lists for recall. The [documentation study guide](/resources/cambridge-igcse-ict-0417-documentation/) explains each component, and the [documentation practice questions](/resources/cambridge-igcse-ict-0417-documentation-practice/) test you on scenarios.

## Purpose in one line each

- **Technical documentation**: lets technicians and programmers **maintain, repair and upgrade** the system, even if they did not build it.
- **User documentation**: lets users **use the system** and **solve common problems** without help.

## Characteristics

| Technical | User |
|---|---|
| Written for specialists | Written for non-specialists |
| Technical terms, code, diagrams | Plain language, screenshots, step-by-step |
| Explains how the system works | Explains how to use the system |
| Used when changing the system | Used when working with the system |

## Component checklist

### Only in technical documentation

- Program listing
- Program language
- Program flowcharts/algorithms
- System flowcharts
- File structures
- List of variables
- Validation routines

### Only in user documentation

- How to load/run/install software
- How to save a file
- How to print data
- How to add records
- How to delete/edit records
- Error messages
- Error handling
- Troubleshooting guide/helpline
- Frequently asked questions
- Glossary of terms

### In both (at different depths)

- Purpose of the system
- Limitations of the system
- Hardware and software requirements
- Input format
- Output format
- Sample runs (called sample runs/test runs in the technical list)

## Memory hook

Technical items describe **the inside** of the system (code, data, logic, rules). User items describe **actions** a user takes (install, save, print, add, edit, delete) and **help** when things go wrong (errors, troubleshooting, FAQs, glossary). The six shared items describe **what the system is for and what it looks like from outside**: purpose, limits, requirements, inputs, outputs and examples of it running.

## What each technical component helps a technician do

| Component | Helps the technician to |
|---|---|
| Program listing | See and change the code |
| Program language | Use the right skills and tools |
| Program flowcharts/algorithms | Follow the logic of a program |
| System flowcharts | See how data flows through the whole system |
| File structures | Know the fields, data types and lengths stored |
| List of variables | Understand what each variable holds |
| Validation routines | Check or change the rules on input |
| Sample runs/test runs | Compare output after a change with known correct output |

## Key terms

| Term | Meaning |
|---|---|
| Technical documentation | Documentation explaining how the system works, for those who maintain it |
| User documentation | Documentation explaining how to use the system |
| Program listing | The complete code of the program |
| System flowchart | Diagram of how data passes through the whole system |
| Program flowchart | Diagram of the steps in one program |
| Sample run | Example of the system being used, with input and the output produced |
| Limitations | What the system cannot do |
| Troubleshooting guide | Solutions to common problems |
| Glossary | List of technical terms with their meanings |

## Exam traps

- **Purpose, limitations, hardware and software requirements, input format, output format and sample runs are in both.** Do not claim they belong to only one.
- **Glossary and FAQs are user documentation.**
- **Validation routines and list of variables are technical documentation.**
- **"Easy to understand"** is not a purpose; say what the reader needs to do.
- **Reasons must fit the reader**: a technician needs a program listing to *change* code, not to "learn the system".

## Self-test

1. State the purpose of technical documentation.
2. State the purpose of user documentation.
3. Name three components found only in technical documentation.
4. Name three components found only in user documentation.
5. Name two components found in both.
6. Why does a technician need a list of variables?
7. What is the difference between a system flowchart and a program flowchart?
8. Why should user documentation include a glossary?
9. Which component tells a user what the system cannot do?
10. A new receptionist cannot remember how to change a customer's address. Which component helps?
11. Why does technical documentation include sample runs/test runs?
12. Give one difference in style between technical and user documentation.

## Self-test answers

1. To explain how the system works so that it can be maintained, repaired or upgraded.
2. To explain how to use the system and solve common problems.
3. Any three of: program listing; program language; program flowcharts/algorithms; system flowcharts; file structures; list of variables; validation routines.
4. Any three of: how to load/run/install; how to save; how to print; how to add records; how to delete/edit records; error messages; error handling; troubleshooting guide/helpline; FAQs; glossary.
5. Any two of: purpose; limitations; hardware and software requirements; input format; output format; sample runs.
6. To understand what each variable stores, so code can be changed without errors.
7. A system flowchart shows how data moves through the whole system; a program flowchart shows the steps within one program.
8. Users may not know technical terms used in the guide.
9. Limitations of the system.
10. How to delete/edit records.
11. So that after a change the technician can check the output still matches the known correct results.
12. Technical uses specialist terms, code and diagrams; user documentation uses plain language and step-by-step instructions with screenshots.
