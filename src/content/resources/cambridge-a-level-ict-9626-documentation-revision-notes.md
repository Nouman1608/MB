These notes condense **section 16.6 Documentation** of the Cambridge International AS & A Level Information Technology 9626 syllabus for examination in 2025, 2026 and 2027 (version 4). It is **A Level only** content, examined in Paper 3 (Advanced Theory).

Test yourself with the [practice questions](/resources/cambridge-a-level-ict-9626-documentation-practice/). The [Cambridge A Level IT hub](/boards/cambridge/a-level/ict/) has every topic and the [free diagnostics](/diagnostics/) show where to start.

## The key idea

Different readers need different documents. Always ask: **who reads it, and what do they need to do?**

## Types at a glance

| Type | Reader | Why needed | Typical contents |
|---|---|---|---|
| **Requirements and design** | Client, analysts, designers, developers, testers | Record what was agreed; plan to build and test against; standard for evaluation | User requirements, system and design specifications, DFDs, flowcharts, file structures, form and report layouts, validation rules |
| **Technical** | Programmers, technicians, support staff | Allow the system to be fixed, updated and moved | Commented code, algorithms, data dictionary, file structures, input and output formats, installation and configuration, test results, backup and recovery, known faults |
| **User** | Day-to-day, non-technical users | Learn the system and solve common problems | Start-up and login, step-by-step tasks with screenshots, tutorial, error messages, troubleshooting, FAQ, glossary, help-desk contact |
| **Marketing** | Potential customers and buyers | Describe and promote the system | Features and benefits, screenshots or demo, requirements, price and licence, customer quotes |

## Advantages and disadvantages

| Type | Advantages | Disadvantages |
|---|---|---|
| **Requirements and design** | Clear agreement; developers and testers know the target; evaluation possible | Takes time; out of date if not revised; long and technical |
| **Technical** | Faster, cheaper maintenance; new staff can take over; helps find faults | Hard for non-specialists; must be updated; costly; may reveal security details |
| **User** | Faster learning; fewer help-desk calls; always available; consistent | Costly to produce well; printed copies go out of date; users may not read it |
| **Marketing** | Informs and attracts customers; shows requirements; increases sales | May exaggerate; costs money; goes out of date quickly |

## Which document answers the question?

| Question | Document |
|---|---|
| What did the client ask for? | Requirements |
| What does the customer table look like? | Technical (or design) |
| How do I change my password? | User |
| What does this system cost and offer? | Marketing |
| How do I restore the system from a backup? | Technical |

## Worked example

A hospital installs a new appointments system.

- **Requirements and design:** the agreed list of what the system must do, and the design of its forms.
- **Technical:** the IT team gets the database layout and restore procedure.
- **User:** receptionists get a step-by-step guide to booking an appointment, with screenshots.
- **Marketing:** the supplier produces a leaflet to sell the system to other hospitals.

Each is correct for its reader. Putting the database layout in the receptionists' guide would confuse them.

## Must-know distinctions

- **User** (how to use it) vs **technical** (how it is built and maintained).
- **User** (teaches) vs **marketing** (sells).
- **Requirements** (what is needed) vs **design** (how it will be done).
- **Written early** (requirements, design) vs **completed late** (technical, user).

## Quick self-test

1. Who reads technical documentation?
2. Name two items in user documentation.
3. Name two items in technical documentation.
4. Give one reason requirements documentation is needed.
5. Which type of documentation describes the price of a system?
6. Why might a printed user guide become a problem?
7. Name the document that tells a technician how to restore the system after a fault.
8. Give one disadvantage of technical documentation.
9. What do design documents contain that user documents do not?
10. Give one advantage of marketing documentation.

### Answers

1. Programmers, technicians and support staff.
2. Any two: step-by-step instructions, screenshots, tutorial, error messages and what to do, troubleshooting, FAQ, glossary, help-desk contact.
3. Any two: commented code, algorithms, data dictionary, file structures, input and output formats, installation instructions, test results, backup and recovery procedures.
4. Any one: to record what was agreed; to give developers and testers a target; to allow the finished system to be evaluated.
5. Marketing documentation.
6. It goes out of date when the software is updated.
7. Technical documentation.
8. Any one: hard for non-specialists to understand; must be updated with every change; time-consuming and costly to write.
9. Data flow diagrams, flowcharts, file and database structures, validation rules and screen and report layouts.
10. Any one: tells customers what the system can do; helps to sell it; shows the requirements before purchase.

## Where marks are usually lost

- Saying "user documentation has the code".
- Not naming the reader of the document.
- Describing contents of one type with items from another.
- Treating marketing documentation as a user guide.
- Giving advantages only.
- Saying documentation is "written at the end" only.

## Frequently asked questions

**Who needs technical documentation?**
Programmers, technicians and support staff who install, maintain or change the system, especially after the original developers have left.

**What should user documentation include?**
Step-by-step instructions for tasks, screenshots, a tutorial, explanations of error messages, troubleshooting advice and help-desk contact details.

**Is marketing documentation part of the 9626 syllabus?**
Yes. Section 16.6 lists user and marketing documentation along with requirements, design and technical documentation.
