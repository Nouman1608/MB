## Questions

**1.** State the **three** aspects of a new system that are judged in an evaluation. **[3]**

**2.** State the **three** evaluation techniques named in the syllabus. **[3]**

**3.** A bus company introduced a smartcard payment system six months ago. The user requirements specification said that passengers must be able to pay in under 5 seconds, that drivers must be able to see whether a card is valid, and that the manager must receive a daily takings report.

**(a)** Describe how the company could evaluate the system by checking it against the user requirements specification. **[3]**
**(b)** Describe how feedback from users could be collected from passengers and from drivers. **[3]**
**(c)** Explain why checking against the specification may not find all the problems with the system. **[2]**

**4.** Explain what is meant by *efficiency* when evaluating the bus company's new system, and give **two** measures that could be used. **[3]**

**5.** Explain what is meant by *ease of use* when evaluating the system, and give **two** ways it could be judged. **[3]**

**6.** Describe what is meant by the system being *appropriate for its intended use*. **[2]**

**7.** The evaluation of the smartcard system found the following:

- Payments take 3 seconds on average. Requirement met.
- Drivers' screens show a red or green light, but the light is hard to see in sunlight. Requirement partly met.
- The daily report is produced but has the wrong total when two cards are used for one journey. Requirement not met.
- Many older passengers say they find the system confusing and do not know how to top up.

Evaluate the system, using the three aspects from Question 1, and recommend what the company should do. **[6]**

**8.** Explain why an evaluation should be carried out some months after the system has been introduced and not on the first day. **[2]**

## Answers

**1.** Efficiency [1]; ease of use [1]; appropriateness for the intended use. [1] **[3]**

**2.** Checking against the specifications [1]; meeting user requirements [1]; feedback from users. [1] **[3]**

**3. (a)** Take each requirement in the user requirements specification in turn [1]; test or measure whether it is met, for example time a sample of payments, check the driver's display with valid and invalid cards, and check the daily report against the actual takings [1]; record each as met, partly met or not met, with evidence. [1] **[3]**
**(b)** Passengers: questionnaires or short surveys (for example at stops or on the company's app) [1]. Drivers: interviews or a focus group, or observation of them using the system [1]. Also accept help-desk complaint records and error logs as a source for either group. [1] **[3]**
**(c)** The specification may have been incomplete or wrong, so the system can meet every requirement and still be hard to use [1]; the specification does not cover users' experience, such as confusing screens or the system being slow at busy times. [1] **[2]**

**4.** Efficiency is how well the system uses time, effort, money and resources [1]. Any two measures: time taken to pay; number of passengers served per minute; staff time spent on cash handling or on producing the daily report; running costs compared with the old system; number of breakdowns. [1 each] **[3]**

**5.** Ease of use is how easily and quickly people can learn and use the system [1]. Any two ways: how long it takes new users to learn; the number of mistakes users make; user opinions in a questionnaire; whether the help and instructions are clear; observation of passengers using the readers. [1 each] **[3]**

**6.** The system does the tasks it was built to do for the people who use it [1], and suits the setting, equipment and organisation in which it is used (for example it works on buses in all weather). [1] **[2]**

**7.** Efficiency (up to 2 marks): payment time of 3 seconds beats the requirement [1]; but the wrong daily totals when two cards are used waste the manager's time in checking [1].
Ease of use (up to 2 marks): the sunlight problem makes the driver's light hard to see [1]; older passengers find it confusing and cannot top up, so the user interface or the instructions need improvement. [1]
Appropriateness (up to 1 mark): the system is not fully appropriate for its purpose, since wrong takings undermine the report and some of the passengers cannot use it. [1]
Recommendation and judgement (1 mark): for example correct the report calculation first, as it is a requirement not met; improve the driver display and add clear top-up help for passengers; and re-evaluate. [1]
Maximum 6. **[6]**
*Examiner insight:* Use the three aspects as headings and reach a judgement. Facts copied from the question without comment earn little.

**8.** Problems such as rare faults, heavy-use delays or confusing procedures only show up after real use over time [1]; users also need time to learn the system, otherwise early comments reflect unfamiliarity and not real weaknesses. [1] **[2]**

## Where marks are usually lost

- Writing "the system works" without evidence.
- Giving only strengths, or only weaknesses.
- Not using the three aspects in an "evaluate" answer.
- Describing testing before release instead of judging after use.
- Using one technique only.
- Having no conclusion or recommendation.

## Frequently asked questions

**What does an evaluate question require?**
It requires a judgement. You should weigh strengths and weaknesses using the scenario and reach a conclusion.

**How is evaluation different from testing?**
Testing checks a system for faults before release. Evaluation judges, after use, how well the system meets its requirements and the needs of its users.
