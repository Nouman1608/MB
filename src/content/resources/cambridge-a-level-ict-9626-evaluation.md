This guide goes deeper into section **16.7 Evaluation** of the Cambridge International AS & A Level Information Technology 9626 syllabus for examination in 2025, 2026 and 2027 (version 4). It is **A Level only** content examined in Paper 3 (Advanced Theory), where calculators are not allowed.

The syllabus asks you to know:

- how to **evaluate a new system**, including its **efficiency, ease of use and appropriateness for intended use**
- the **evaluation techniques**: checking against specifications, meeting user requirements, and feedback from users.

## What evaluation is for

Evaluation is the stage in which the organisation asks: *did we build the right system, and does it work well?* It happens after the system has been in use long enough for real problems to show, not on the first day. The result is an **evaluation report** that records strengths, weaknesses and recommendations.

Evaluation is the link that turns the life cycle into a cycle. Weaknesses may lead to maintenance, and new needs may start a fresh round of analysis.

The command word matters. In the syllabus, **evaluate** means to judge the quality, importance, amount or value of something. A good answer therefore does not just list facts: it weighs strengths against weaknesses and reaches a conclusion.

## What is judged

### Efficiency

Does the system use time, effort, money and resources well?

Questions to ask:

- Is each task faster than it was with the old system? (For example, how long does it take to process one order?)
- Does it use less staff time and fewer materials such as paper?
- Does it run quickly and reliably, without long waits or crashes?
- Does it use storage, network capacity and hardware sensibly?
- Are running costs lower than before?

### Ease of use

Can people use it with little effort?

Questions to ask:

- How long does a new user take to learn it?
- Are the screens, menus and forms clear and consistent?
- Do users make many mistakes, and are the error messages helpful?
- Is there good help and user documentation?
- Can people with special needs use it, for example with large text?

### Appropriateness for intended use

Does it suit the job, the users and the setting?

Questions to ask:

- Does it do the tasks it was built to do, and nothing important is missing?
- Does it fit the working environment and the equipment that is available?
- Is the size and cost of the system sensible for the organisation?
- Does it cope with the volume of data and number of users?
- Is it secure and does it follow the law?

## Evaluation techniques

### Checking against specifications

Compare the finished system with the **user requirements specification** and the **system and design specifications**. For each item, decide whether it has been met, partly met or not met, and note evidence.

- *Strength:* objective and systematic, since each requirement is checked.
- *Weakness:* a system can meet every requirement and still be awkward to use, because the requirements may have been wrong or incomplete.

### Meeting user requirements

Test whether the system does what the **users** need in everyday work. This is close to the first technique but looks at real tasks. Users or evaluators run through typical tasks (such as "enrol a new student") and judge whether the result is what they need.

- *Strength:* tests the system against real needs.
- *Weakness:* depends on the tasks chosen; needs time and users' cooperation.

### Feedback from users

Collect users' opinions and experiences by questionnaires, interviews, observation, user focus groups, help-desk records or logs of errors.

- *Strength:* shows problems and good points that specifications do not cover, such as frustration or confusing screens.
- *Weakness:* opinions are personal; some users may complain about change, not about the system; the people who respond may not represent everyone.

Good evaluation uses **all three** techniques, because each catches things the others miss.

## Worked example: an evaluation table

A nursery introduced an online system for booking sessions and sending invoices. Six months later the manager evaluates it. The checking against the user requirements specification gives:

| Requirement | Evidence | Result |
|---|---|---|
| Parents can book a session online | Tested with 5 parents; all booked in under 3 minutes | Met |
| Invoices are produced automatically each month | Run for 6 months; all produced | Met |
| Staff can see who is in on a given day on one screen | Screen exists but does not show children's allergies | Partly met |
| The system sends reminders by text message | Not built; budget ran out | Not met |

Feedback from users, collected by a questionnaire to staff and parents:

- Parents found booking easy but said the confirmation email was slow to arrive.
- Staff said the daily list screen was cluttered and took them a long time to read.

Judgement by criterion:

- *Efficiency:* invoicing went from two days of manual work to a few minutes, so efficiency has improved a great deal. Slow email confirmations are a weakness.
- *Ease of use:* booking is easy, but the staff screen is cluttered.
- *Appropriateness:* the missing allergy information is a safety problem for a nursery, so the system is not yet fully appropriate for its intended use.

*Recommendations:* add allergies to the daily list (this is urgent), simplify the layout, fix the email delay and decide whether to add text reminders.

Notice how the report is balanced, links each point to evidence and ends with actions.

## Writing an evaluation answer

1. Choose the criteria (efficiency, ease of use, appropriateness).
2. For each, give a point for and a point against, using the scenario.
3. Say which evaluation technique would find each point.
4. Finish with a judgement and, if useful, a recommendation.

## Common errors

- Writing only that the system "works well" without saying how or for whom.
- Only giving strengths or only giving weaknesses.
- Evaluating before the system has been used for a realistic period.
- Using only one technique and ignoring the others.
- Confusing evaluation with testing. Testing checks the system works before release; evaluation judges how well it meets needs after use.
- Not linking comments to the scenario.

## Frequently asked questions

**What three things are judged in an evaluation?**
Efficiency, ease of use and appropriateness for the intended use.

**What are the evaluation techniques in the syllabus?**
Checking against specifications, meeting user requirements, and feedback from users.

**What is the difference between testing and evaluation?**
Testing looks for faults before the system is released. Evaluation judges, after use, how well the system meets its requirements and the needs of users.
