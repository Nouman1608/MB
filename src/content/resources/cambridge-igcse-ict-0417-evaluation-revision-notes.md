Section 7.6 of Cambridge IGCSE ICT 0417 covers evaluating a solution once it is in use. These notes give the syllabus phrases you should use, the evidence behind each, and a self-test. The [evaluation study guide](/resources/cambridge-igcse-ict-0417-evaluation/) has a worked requirements check, and the [evaluation practice questions](/resources/cambridge-igcse-ict-0417-evaluation-practice/) test you on scenarios.

## Syllabus coverage

| Syllabus wording | Recall |
|---|---|
| Evaluate a solution including the efficiency, the ease of use and the appropriateness of the solution | Three qualities judged with evidence |
| Compare the solution with the original task requirements | Go through the requirements specification point by point |
| Identify any limitations and necessary improvements | Each limitation matched with a specific improvement |
| Evaluate the users' responses to the results of testing the system | Collect and weigh user feedback |

## The seven phrases to use

1. **Efficiency** of the solution.
2. **Ease of use** of the solution.
3. **Appropriateness** of the solution.
4. **Compare** with the **original task requirements**.
5. Identify **limitations**.
6. Identify **necessary improvements**.
7. Evaluate **users' responses** to the **results of testing**.

## What each means and the evidence for it

| Element | Question it answers | Evidence |
|---|---|---|
| Efficiency | Does it save time and resources? | Task times before and after; staff needed; errors; paper and storage used |
| Ease of use | Can the intended users operate it easily? | Questionnaires; interviews; observation; help requests; training time; input errors |
| Appropriateness | Is it the right solution for this organisation and its users? | Fit with users' skills, working environment, budget and purpose |
| Requirements comparison | Does it do what was agreed? | Requirements specification checked: met, partly met, not met |
| Limitations | What can it not do, or do poorly? | Requirements not fully met; user complaints; observed problems |
| Improvements | What specific change would fix each limitation? | Matched to each limitation |
| Users' responses | What do users think of the results of testing? | Feedback forms, comments, reported problems |

## When evaluation happens

- After **implementation**, once the system has been used for some time.
- Users need time to get used to the system, so early complaints about unfamiliarity do not distort the results.
- Findings can start a new cycle of **analysis**.

## Limitation → improvement pairs (examples)

| Limitation | Improvement |
|---|---|
| Reports cannot be filtered by date | Add a date filter to the report screen |
| System slow when many users log in | Upgrade the server or increase network bandwidth |
| Customers cannot book on mobile phones | Develop a mobile-friendly version of the booking page |
| No backup of daily data | Add automatic daily backup to cloud storage |
| Staff confused by the menu | Simplify the menu and add on-screen help |

## Efficiency versus ease of use

- **Efficient but not easy to use**: very fast processing, but users must remember codes and many steps.
- **Easy to use but not efficient**: friendly screens, but each order takes several slow pages.
- Judge each separately, with its own evidence.

## Key terms

| Term | Meaning |
|---|---|
| Evaluation | Judging how well the new system meets its purpose and requirements |
| Efficiency | How well the system uses time and resources |
| Ease of use | How easily the intended users can operate the system |
| Appropriateness | How well the solution suits the organisation, users and task |
| Original task requirements | What the system was agreed to do, in the requirements specification |
| Limitation | Something the system cannot do, or does poorly |
| Improvement | A specific change that removes a limitation |
| Users' responses | Users' feedback on how the system performed in testing |

## Exam traps

- **"See if it works"** is testing, not evaluation.
- **"Make it better"** is not an improvement: name the change.
- **Efficiency ≠ ease of use.**
- **Requirements come from analysis**: say "original task requirements" or "requirements specification".
- **Users matter**: always include gathering users' responses.
- **Timing**: evaluation is after the system is in use, not before implementation.

## Self-test

1. State the three qualities of a solution that the syllabus says are evaluated.
2. What is the solution compared with during evaluation?
3. Give two ways of measuring the efficiency of a new system.
4. Give two sources of evidence about ease of use.
5. What does appropriateness of a solution mean?
6. Define a limitation.
7. A new system cannot print invoices in colour, which was a requirement. Suggest an improvement.
8. Why must evaluation take place after the system has been used for a while?
9. How can users' responses to the results of testing be collected?
10. Give an example of a system that is efficient but not easy to use.
11. Why is comparing with the original requirements the most objective part of evaluation?
12. What happens to the list of improvements produced by evaluation?

## Self-test answers

1. Efficiency, ease of use, appropriateness.
2. The original task requirements (requirements specification).
3. Any two of: compare task times with the old system; count staff needed; count errors; measure paper or storage used.
4. Any two of: questionnaires; interviews; observing users; number of help requests; training time needed.
5. Whether the solution suits the organisation, its users and the task it was built for.
6. Something the system cannot do or does poorly.
7. For example: connect a colour printer and add a colour option to the invoice layout.
8. Users need to be familiar with it, and enough real use is needed for reliable evidence.
9. Questionnaires, interviews or feedback forms after users have seen the test results.
10. For example: a system that processes orders very quickly but needs users to type long codes from memory.
11. The requirements were agreed before the system was built, so each can be checked as met or not met.
12. It can be acted on, and often starts the analysis for the next version of the system.
