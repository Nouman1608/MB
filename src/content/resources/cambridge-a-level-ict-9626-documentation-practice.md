These questions cover **section 16.6 Documentation** of the Cambridge International AS & A Level Information Technology 9626 syllabus for examination in 2025, 2026 and 2027 (version 4). This is **A Level only** content examined in Paper 3 (Advanced Theory), where calculators are not allowed. All questions can be answered on paper.

## Questions

**1.** State **three** types of documentation that may be produced for a new system. **[3]**

**2.** A dental practice has bought a new appointment system.

**(a)** State who would use the user documentation and describe **three** items it should contain. **[4]**
**(b)** State who would use the technical documentation and describe **three** items it should contain. **[4]**
**(c)** The practice manager says: "The technical documentation is not needed, because nothing is wrong with the system." Explain why the manager is wrong. **[2]**

**3.** Describe the purpose of requirements and design documentation. **[3]**

**4.** The company that wrote the appointment system wants to sell it to other dental practices.

**(a)** Name the type of documentation it should produce for this purpose. **[1]**
**(b)** Describe **three** items it could include. **[3]**
**(c)** Give **one** disadvantage of this type of documentation. **[1]**

**5.** For each of the following, name the type of documentation that would be used.

**(a)** A receptionist wants to know how to cancel a booking. **[1]**
**(b)** A technician needs to know the field names and data types in the patient table. **[1]**
**(c)** A tester wants to know what the system was supposed to do. **[1]**
**(d)** A practice manager is comparing the system with a rival product. **[1]**

**6.** Give **two** advantages and **two** disadvantages of providing user documentation as an online help system instead of a printed manual. **[4]**

**7.** A senior programmer leaves the company that wrote the appointment system. The company finds that she did not write any technical documentation.

Discuss the problems this may cause. **[5]**

## Answers

**1.** Any three, one mark each: requirements (and design) documentation; technical documentation; user documentation; marketing documentation. **[3]**

**2. (a)** The receptionists, dentists and other staff who use the system every day. [1] Any three: how to log in and log out; step-by-step instructions for tasks such as booking or cancelling, with screenshots; a tutorial or quick-start guide; explanations of error messages; troubleshooting advice or FAQ; help-desk contact. [1 each] **[4]**
**(b)** The programmers, technicians and support staff who maintain the system. [1] Any three: commented code or algorithms; the database structure and field data types; input and output formats; installation and configuration instructions; backup and recovery procedures; test results; known faults. [1 each] **[4]**
**(c)** Technical documentation is needed in order to maintain the system and not only to repair it [1]; it is used for updates, upgrades and moving the system to new hardware, and for when the original developers are unavailable. [1] **[2]**
*Examiner insight:* "It is needed in case something goes wrong" gains one mark at most; add a second use such as updating or training new support staff.

**3.** It records what the client and developers have agreed that the system must do [1]; it gives developers a plan to build from and testers a standard to test against [1]; it allows the finished system to be evaluated against the original requirements. [1] **[3]**

**4. (a)** Marketing documentation. [1] **[1]**
**(b)** Any three: a description of the features and benefits; screenshots or a demonstration; hardware and software requirements; prices and licence terms; comments from satisfied customers; contact details. [1 each] **[3]**
**(c)** Any one: may exaggerate and disappoint customers; costs money to produce; goes out of date quickly. [1] **[1]**

**5. (a)** User documentation. [1]
**(b)** Technical documentation. [1]
**(c)** Requirements documentation (design documentation also accepted). [1]
**(d)** Marketing documentation. [1] **[4]**

**6.** Advantages (any two): always up to date because the supplier updates it once; searchable, so users find help quickly; can include video and links; no printing cost. [1 each]
Disadvantages (any two): needs a computer, and maybe internet access, to read; hard to use while the system itself is on the screen; some users prefer paper; may not be available if the system fails. [1 each] **[4]**

**7.** Any five, one mark each (up to 4 for problems, 1 for a conclusion or development):
- No record of the code or structure, so other programmers must work it out, which is slow and costly. [1]
- Faults take longer to find and fix, so the dental practices have longer outages. [1]
- Changes may introduce new faults because nobody understands how the parts depend on each other. [1]
- New staff cannot be trained quickly. [1]
- Upgrades or moving to new hardware become difficult or impossible. [1]
- Conclusion: the company should create the documentation by studying the system, and make it a rule that it is written during development. [1] **[5]**
*Examiner insight:* "Discuss" needs several developed points. Each problem should lead to a consequence for the company or the practices.

## Where marks are usually lost

- Not saying who the reader of each document is.
- Putting program code in user documentation.
- Treating marketing documentation as a user manual.
- Giving advantages only.
- Describing a purpose as "to record the system" without saying what for.

## Frequently asked questions

**How do I decide which document to name in an exam question?**
Look at who is reading it and what they need. A user who needs to complete a task needs user documentation, and a technician who needs the structure of the data needs technical documentation.

**Do I need to learn the contents of each type?**
Yes. The syllabus asks for the contents of the different types of documentation, as well as why each is needed.
