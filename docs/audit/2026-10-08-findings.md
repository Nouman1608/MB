*Repair verification, round three. The subject of this round is a correction that worked, and
a mistake this audit made while reporting it.*

## The repair is complete, and better than the finding asked for

**D-211** (`01f08fc`) corrected the mark-scale regression across seven files — the five E900
named and two more found by corpus search. All five named resources were read on `main` to
confirm it:

| | state now |
|---|---|
| eAssessment passages | **24 marks per criterion** (criteria A, B, C, D) |
| classroom passages | **8 achievement levels**, 32 total across four criteria |
| the propagated derived total | corrected **96 → 72** |
| explicit two-scale statement | **in all five files** |

The syllabus guide carries a dedicated section:

> **## Two mark scales — do not mix them up**
> … Thirty-two is not a valid eAssessment mark total for any single criterion.

E900 asked for the numbers to be changed and the two scales stated side by side *once*. What
was done states the distinction in **every** file, so the ambiguity that caused the original
defect cannot recur by reading any one of them in isolation. That is a better fix than the
correction specified.

D-211's own commit message also adopts, in its own words, the rule Q362 recommended, and
describes the reversal it is undoing as its own error.

## The finding against this audit

**The index this audit published to orient the repair work said five files "are currently
wrong". They were not.**

| | |
|---|---|
| D-211 landed | 2026-09-15, 00:02 |
| the README claiming the files are wrong | 2026-09-15, 14:15 |
| gap | **fourteen hours** |

The claim was carried forward from a read taken at `cc7d589` into a new document, and the
current state was never re-checked. The regression document itself was accurate about what it
saw; the index repeated its conclusion as a present-tense status long after it had stopped
being true.

**This is the same failure this audit recorded against itself once before.** Q350 recorded
mistaking a three-day-old local directory for the current branch, and `snapshot_provenance.py`
was written so it could not recur. That tool records the provenance of a *snapshot*. It does
nothing about a *conclusion* carried into a new document — which is the form the failure took
this time.

The rule, now in the README:

> **A finding is a timestamp, not a status.** It records what was true when it was written.
> Before acting on one — or repeating it — check the file as it stands now. This cuts both
> ways: the audit has published a stale alarm about files that were already fixed, and a
> repair round has closed a finding against a snapshot that was three days old.

Note for correction, and it is against this audit rather than the repair. The index this audit published to orient the repair work told a reader that five files are currently wrong. They were not.
