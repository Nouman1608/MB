# Marlbridge audit — fixing the count, and finding the same defect twice more

*Repair verification, round one, continued. Q364 recorded that this audit had been publishing
an open figure 131 too high. This is the fix, and what applying it turned up.*

---

## The fix

The reconciliation against the decision log now happens **inside the build**. A new module,
`work/marlbridge-audit/decision_log_closures.py`, holds the identifiers each decision-log
entry says it closed together with the commit that carries it, and enforces three separations
that had previously been made by hand each time and could have been lost:

1. **Deferred is not closed.** A range that sweeps up a deferred finding does not close it.
2. **A qualifier is not a closure.** "E712–E748 (nearly all)" closes none of that range,
   because the commit does not say which are left. Neither does "partial", nor "could not be
   located in the corpus".
3. **A declared closure this audit has verified is *not* closed stays open.** This is the rule
   that matters most, and it is new. It keeps **E782** — the D-202 reversal recorded as E900 —
   out of the closed set, rather than letting it be swept in by the range that contains it.

| | before | after |
|---|---|---|
| confirmed errors counted open | 842 | **712** |
| declared closed by the decision log | not tracked | **130** |
| still open despite a closing round | not tracked | **48** |

The caveat now travels with the number in the published output rather than being left for a
reader to supply: *declared closed means a repair round recorded the finding as handled, not
that this audit has verified it.*

---

## Two more instances of the same defect

### 1. The published prose carried the count as a hardcoded number

The scope paragraph that opens **every report this audit generates** did not compute the open
figure at all. It read `827` as a literal, against a computed `842`.

**The prose and the data block of the same document had been disagreeing with each other by
fifteen**, in every version published for as long as that literal had been stale. This is
worse than the original defect, which was at least a computation that had stopped being
re-run.

It is now substituted from the computed value, and the build asserts that the placeholder
never survives into the output.

### 2. The validation gate could not run on the days it was needed

`validate.py` had the repository root written into it as an absolute Windows path. On the
several days when the Windows shell was down and only the Linux mount was available, **the
gate could not run at all** — which is precisely when a stale artefact is most likely and an
unrun check least likely to be noticed.

`slugcheck.py`, which guards every append to the findings record, had the same defect and
failed the moment it was run from the other shell.

Both now derive the root from their own location.

---

## The count, taken rather than estimated

**34** of the audit's own scripts carry the same hardcoded path. **4** are on the critical
path of building and validating the report; two of those were already portable and the other
two are fixed here. The remaining **30** are analysis scripts run by hand.

**Those 30 have deliberately not been swept.** A thirty-file mechanical edit at the end of a
long working session is the exact shape of change this audit has repeatedly found to be
unsafe — most recently when a mechanical tier-annotation of 59 corrections was generated,
inspected and voided before publication.

That decision was vindicated within the minute. `gen_findings.py` was needed next, so it was
made portable one file at a time per the rule — and it required **three** `dirname()` calls
where two were correct in a script fixed moments earlier, because the two files sit at
different depths. A uniform mechanical edit would have silently pointed it at the wrong
directory.

---

## The tenth validation step

The gate had nine steps and all nine passed, every run, on a number that was 131 too high.
They passed because **every one of them compared the record with itself**: `open 842 = 2 + 6 +
834` is internally consistent and externally false.

Step 5b compares the record with the decision log. It is the only one of the ten that looks
outside the artefact:

```
5b. declared closed by decision log 130 ; overlap with open 0 OK ; caveat published: True ; still open despite a closing round 48
```

The general form, worth keeping: **a validator that only ever compares a record to itself
cannot detect that the record has stopped tracking the world.** It is not a weak check; it is
a check of a different thing.

## Q365 - The stale open count is fixed inside the build, and applying the fix found the same defect twice more, once as a hardcoded number in the published prose [Questionable claim, Medium]

- **Files:** `a-level-aqa-economics-measurement-of-macroeconomic-performance`
- **Where:** The build pipeline and the scope paragraph it publishes
- **Locate by:** `title: "AQA A-Level Economics: The Measurement of Macroeconomic Performance (7136)"`

**What is wrong.** The preceding finding recorded that the open figure this audit publishes had drifted a hundred and thirty-one above the real one, because the remediation record was never reconciled against the decision log and every validation step compared the figure only with itself. The reconciliation now happens inside the build. A single module holds the identifiers each decision-log entry says it closed, together with the commit that carries it, and it enforces three separations that had previously been made by hand and could have been lost: a finding a closing commit called deferred is not closed, a finding it qualified as partial or unlocatable is not closed, and a finding this audit has since verified is not in fact closed is not closed either, which keeps the reversal recorded earlier in this round out of the closed set rather than letting it be swept in by the range that contains it. The reconciled figure is seven hundred and twelve rather than eight hundred and forty-two, a hundred and thirty having been declared closed, and the caveat that declared closed means a repair round recorded the finding as handled rather than that this audit verified it is now published beside the number rather than left to a reader to supply. Applying the fix exposed two further instances of the same defect. The first is worse than the original: the scope paragraph that every published report opens with carried the open count as a hardcoded number rather than a computed one, and it read eight hundred and twenty-seven against a computed eight hundred and forty-two, so the prose and the data block of the same document had been disagreeing with each other by fifteen. It is now substituted from the computed value and the build fails if the placeholder survives into the output. The second explains the silence: the validation gate had the repository path written into it as an absolute Windows path, so on the several days when only the other shell was available the gate could not run at all, which is precisely when it was most needed. The marker-and-slug checker that guards every append had the same defect and failed the moment it was run from the other shell. Both now derive the root from their own location. A count of the rest was then taken rather than estimated: thirty-four of the audit own scripts carry the same hardcoded path, of which four sit on the critical path of building and validating the report and two of those four were already portable. The remaining thirty are analysis scripts run by hand, and they have deliberately not been swept, because a thirty-file mechanical edit at the end of a long working session is the precise shape of change this audit has repeatedly found to be unsafe, and nothing depends on them running unattended. Note for correction: a tenth validation step has been added, and it is the only one of the ten that compares the record with something other than itself.

**Fix.** Keep the reconciliation inside the build rather than performing it by hand, never publish a count as a literal where it can be computed, treat any validation step that compares the record only with itself as unable to detect staleness by construction, and make the remaining thirty scripts portable one at a time as each is next needed rather than in a single sweep.
