## Q369: three routes, two of which fail in ways that look alike

Worth recording, because the same three routes will be met on every remaining document in this
workstream.

**1. Ordinary fetch — retrieves, then truncates deterministically.** 135,110 characters,
stopping at the identical mid-word point on every attempt. Because *the byte count and the
stopping point reproduce exactly*, this is a property of the retrieval path, not a transient
failure. A single occurrence looks like a flaky connection; the second occurrence is what
tells you it never will succeed.

**2. Direct download — a bot challenge.** A 5,732-byte Cloudflare interstitial instead of the
document; retrying with a browser user-agent returned the same challenge at 5,987 bytes.
**That challenge was not circumvented and must not be.** That it is trivially detectable does
not make working around it acceptable.

**3. Browser session — the document, whole.** The challenge resolves as it does for any
reader, the PDF arrives at 4,896,543 bytes with a `%PDF-1.6` header, and pdf.js injected at
the document's own origin extracts every page.

**The third route is the one this audit already owned.** It is the same technique used to
resolve the two-column tier question on Cambridge 0620. The capability was not new — the
blocker had been standing for want of trying it here.

The lesson for the log: **a failed download that returns a challenge page is not evidence that
a document is unavailable, and a truncated fetch that returns the same byte count twice is not
evidence of a flaky connection.** The two look similar in a log and mean entirely different
things.
